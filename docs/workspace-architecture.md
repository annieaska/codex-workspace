# 工作空间编排架构

## 目标

工作空间规则的价值不是把所有知识塞进每次会话，而是让 Codex 在正确的时机读取正确的最小信息。理想状态是：常驻规则短、任务资料按需、项目状态单一、工具证据可回查。

## 三层结构

### 1. 常驻规则层

根目录 `AGENTS.md` 只放跨任务长期有效的约束，例如执行边界、安全、验证强度、上下文工作集和按需能力路由。它不应该承载项目历史、长篇 SOP 或工具手册。

### 2. 按需文档层

把只对特定任务生效的流程放在独立文档中，并在 `AGENTS.md` 中保留一张很短的路由表。命中任务时读取对应章节，未命中时不加载。

示例：

| 任务类型 | 按需读取 |
| --- | --- |
| 长上下文、压缩或跨窗口 | 上下文与交接规则 |
| 软件修改或测试 | 软件 QA 工作流 |
| 视觉或页面交付 | 视觉规范与验收规则 |
| 发布或外部写入 | 发布清单与权限边界 |

### 3. 项目状态层

长任务使用项目自己的 `PROJECT.md` 保存当前交付周期。它是唯一状态真源，只记录仍会影响下一步的事实。详细报告、日志和产物保留文件路径，不复制进状态摘要。

## 推荐执行循环

1. 从用户请求和当前仓库状态确定目标、验收与明确不做项。
2. 读取适用的最小规则和项目状态锚点。
3. 建立本任务唯一活跃工作集，并确定第一动作和验证门禁。
4. 执行小而可审查的改动；大输出先过滤或落盘。
5. 只运行与变更和真实风险对应的定向验证。
6. 长任务更新既有状态锚点；短任务直接交付，不制造新的状态文件。

## 为什么能减少上下文膨胀

- 常驻提示不再重复携带低频规则和项目历史。
- 历史记忆从自动注入改为缺事实时主动查询。
- 完整日志、图片和工具对象留在文件系统，只携带结论和定位信息。
- 单一状态真源消除了多个摘要之间的重复与冲突。
- 恢复任务时先读增量锚点，不默认重放完整历史。

## 文件归属与临时输出

目录应按稳定用途组织，并保留一个项目入口。项目是否进行中或已完成可以记录在项目状态中；是否分目录取决于现有结构，不为整理而强制增加两套目录。

| 文件用途 | 归属原则 |
| --- | --- |
| 项目过程、成果、临时文件 | 跟随实际项目真源，分别进入现有工作区、交付和临时位置 |
| 可复用研究、通用素材 | 进入已有知识或业务资料分类 |
| 新收到但用途未定的原件 | 进入收件位置，待确认后归位 |
| 无项目的临时输出 | 进入统一临时位置，按日期和任务区分 |
| 迁移恢复副本 | 单独标明保留用途，不能按普通缓存清理 |

生成前明确输出目录和工具工作目录，生成后核对实际路径。仅写规则不能保证工具遵守：独立工作副本、默认输出位置和固定工具缓存都应按实际环境验证。维护一份文件导航和既有迁移记录即可，不另建第二套项目状态系统。

迁移应先核对引用和项目真源，再按原包结构归位并修正入口。用途不明的文件先保留；清理空壳前核实目录内容，并使用可恢复方式。目录名称含“临时”不构成删除授权。

公开仓库只保存这些通用规则与模板。实际业务资料、个人导航、工具配置和恢复副本保留在本地；需要远端备份时使用另行确认的私有目的地。不要把含私人历史的本地分支直接合入公开模板仓库。

## 如何验证

不要用配置文件字符数直接推断 Token 节省。选择几类真实任务，对比优化前后的初始上下文、工具返回量、记忆召回量、完成质量和实际使用量。只保留能稳定改善结果的规则。
