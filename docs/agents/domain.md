# Matt 领域资料读取规则

## 读取顺序

1. 先定位并读取当前项目的 `PROJECT.md`，确认目标、范围、当前状态、下一动作和已确认决策。
2. 只在任务需要时读取项目的 `01_输入` 和 `02_工作区` 中直接相关材料。
3. 按需检索 `03_知识库` 的领域事实与方法、`04_能力库` 的能力定义／SOP／模板、`05_确认记录` 的人工确认事实与决策。
4. 仅在需要执行器、环境或连接信息时读取 `06_系统说明`；禁止从中寻找或写入密钥。

## 真源边界

- 项目状态和项目决策：以项目 `PROJECT.md` 为准。
- 可复用能力定义：以 `04_能力库` 为准；项目实例不得反向成为能力定义真源。
- 人工确认的业务事实、偏好、决策和经验：以 `05_确认记录` 为准。
- `architecture.md`、ADR、Matt 的 `map.md`、`spec.md` 和工单只描述当前执行过程，不能覆盖以上真源。

## 架构与领域模型交接

- `architecture-designer` 先输出并经人工确认架构；`domain-modeling` 后续必须沿用该架构的对象边界、接口和数据流，不得静默改写。
- `domain-modeling` 发现术语冲突或领域边界无法成立时，退回架构门禁并明确列出冲突，不带着矛盾进入 `to-spec`。
- 仅服务当前项目的术语与边界摘要写回 `PROJECT.md`；确认可复用的能力术语写入对应的 `04_能力库` 能力定义。不得为了适配外部 Skill 另建第二份领域真源。
- 架构 ADR 放在当前项目的 `02_工作区/Matt执行/adr/`，只作为决策证据；涉及业务事实或长期能力定义时，仍需摘要写回相应业务真源。

## 禁止重复治理

- 不为 Matt 另建 `CONTEXT.md`、Lifecycle、Project Anchor、交接包或第二份项目状态文件；只有三级架构阶段可按上述门槛建立 ADR。
- 不整库加载知识资料；先用 `rg` 定位，再精确读取与当前任务直接相关的内容。
- 不把临时推断写入 `05_确认记录`，也不把运行时过程文件写入 `06_系统说明`。
